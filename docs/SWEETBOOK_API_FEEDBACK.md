# Sweetbook Book Print API — 연동 피드백

> 실제 Sandbox 키로 연동하며 정리한 기록. 스텁으로 시작해 실검증을 거쳐 실주문까지 간 왕복이 그대로 남아 있다.
> 최종 확인 2026-08-06. 공식 문서를 대조하고 Sandbox로 직접 호출해 확인했다.

## 연동 결과 요약

| 단계 | 결과 |
|---|---|
| Bearer 인증 | ✅ |
| 책 렌더 create → cover → contents → finalization | ✅ 24p `isValid: true` |
| 주문 생성 `POST /orders` | ✅ `or_3oKrIwb1C5Ao` 외 다수, `PDF_READY` |
| 충전금 차감 | ✅ 총액 15,327원에 부가세 10%를 더해 16,850원 차감 |
| 주문 취소와 환불 `POST /orders/{uid}/cancel` | ✅ 제작 시작 전 전액 환불 |
| 웹훅 수신 | ⬜ 미등록. 공개 HTTPS 주소를 확보하면 `PUT /webhooks/config` |

## 잘된 점

- **일관된 응답 봉투** — 모든 엔드포인트가 `success`, `message`, `data`, `errorCode`, `errors`, `fieldErrors`로
  같은 모양을 준다. 덕분에 클라이언트에서 언랩과 에러 처리를 한 곳으로 모을 수 있었다.
  특히 `errorCode`가 문자열 enum이라 `ERR_INSUFFICIENT_CREDIT`을 "충전금이 부족해요"로 바꾸는 분기를
  메시지 문자열 매칭 없이 만들 수 있었다.
- **Bearer 인증과 환경 분리** — Base URL만 다르고 스키마가 같아 설정 하나로 Sandbox와 Live를 오간다.
  충전금도 두 환경이 완전히 분리돼 있어 테스트가 운영 잔액을 건드릴 걱정이 없었다.
- **TEMPLATE 방식의 단계 분리** — create, cover, contents, finalization이 명확히 나뉘어 있어
  렌더러를 순차 호출로 곧게 표현할 수 있었다.
- **`Idempotency-Key`** — 결제성 API에 가장 필요한 장치가 처음부터 있다.
  요청은 타임아웃인데 서버에서는 성공한 경우, 자체 재시도 로직만으로는 이중 차감을 막을 수 없다.
  이 헤더 하나로 해결됐고, 주문 문서에 반드시 포함하라고 못박아 둔 것도 좋았다.
  실패 응답도 24시간 캐시하고 같은 키에 다른 본문이 오면 거부한다는 규약까지 문서에 있어서,
  고정 키를 쓰면 재시도가 잠긴다는 함정을 코드로 옮기기 전에 피할 수 있었다.
- **AI 에이전트용 문서** — `/docs/llms.txt`와 `/docs/llms-full.txt`, 개별 페이지의 `.md` URL을 제공한다.
  문서를 스크래핑할 필요가 없었고, 연동 후반 작업은 합본 하나를 컨텍스트에 넣고 진행했다.

## 헤맨 점

- **`breakBefore`가 쿼리 파라미터** — form-data로 보내면 조용히 무시된다.
  내지 템플릿의 기본값이 같은 페이지에 덮어쓰는 `none`이라, 이걸 놓치면
  24번을 호출해도 페이지 수가 0이 되고 finalization에서 `ERR_INSUFFICIENT_PAGES`로 튄다.
  호출은 매번 201로 성공하기 때문에 원인이 보이지 않는다.
- **충전금 계정 프로비저닝** — 포털에 충전금이 보이는 상태에서도 주문이
  `크레딧 계정이 존재하지 않습니다`로 실패했다. Sandbox 충전금 계정이 별도로 생성된 뒤에야 통과했다.
  에러 메시지만으로는 무엇을 해야 하는지 알 수 없어 한동안 막혀 있었다.
- **판형 단가는 계정마다 다르다** — 문서 예시의 증가분 단가는 500원이지만 우리 계정의 실제 값은 280원이었다.
  화면에 단가를 박아두면 조용히 틀어지는 값이라, `GET /book-specs`로 그때그때 받아오도록 바꿨다.
