# Book Print API 개선 제안 — 파트너 온보딩 관점

> 초안입니다. 제안은 Tripbook을 붙이며 실제로 겪은 것에서만 뽑았고, 근거는 Sandbox 실호출과 커밋에 남아 있습니다.
> 우선순위와 표현은 UiJin이 최종 결정합니다.
>
> 관찰 기간 2026-07-21 ~ 08-06 · 환경 Sandbox · 방식 TEMPLATE
> 결과 책 렌더부터 실주문, 취소·환불까지 완주. 웹훅 수신은 공개 주소가 없어 미등록.

## 왜 이 문서를 쓰는가

Book Print API는 B2B 제품이고, B2B API의 성패는 **파트너가 첫 주문을 성공시키기까지 걸리는 시간**에서 갈린다고 봅니다.
아래는 그 시간을 늘렸던 지점과 각각을 줄일 방법입니다.

대부분은 기능 추가가 아니라 **이미 있는 것에 도달하게 만드는 일**입니다.
제가 막혔던 것의 대부분은 기능이 없어서가 아니라 있는 줄 몰라서였습니다.

## 첫 주문까지 걸어온 경로

| 지점 | 무슨 일이 있었나 |
|---|---|
| 문서 | 개발 문서를 못 찾아 응답을 보고 파라미터 스키마를 역추적하며 시작 |
| 표지·내지 | 다른 엔드포인트가 전부 JSON이라 관성으로 JSON을 보내 415 |
| 내지 누적 | `breakBefore`를 form-data에 넣어 조용히 무시됨 → 24번 호출했는데 0페이지 → finalize에서 `ERR_INSUFFICIENT_PAGES` |
| 주문 | `크레딧 계정이 존재하지 않습니다` — 포털에 충전금이 보이는데도 실패 |
| 뒤늦게 발견 | 공식 Python·Node SDK와 충전금부터 취소까지 전 플로우를 담은 `partner-order-demo`가 이미 공개돼 있었음 |

마지막 줄이 이 문서의 핵심입니다. **제가 며칠 들여 만든 것이 이미 공식으로 제공되고 있었습니다.**
기능의 문제가 아니라 도달의 문제입니다.

## 제안

### P1. 발견 경로 — 가장 싸고 효과가 큽니다

개발 문서가 `noindex`라 웹 검색으로 닿지 않고, 랜딩에서도 `/docs/` 링크가 눈에 잘 띄지 않습니다.
SDK와 데모 앱은 문서 안쪽에 있어, 문서에 도달하지 못하면 함께 놓칩니다.

- 파트너 포털 첫 화면과 **API Key 발급 직후 화면**에 개발 문서·SDK·데모 앱 세 링크를 크게 배치
- API Key 발급 이메일에도 같은 세 링크
- 문서를 검색에 노출하는 것도 고려할 만합니다. B2B 공개 문서는 검색 유입이 파트너 획득으로 이어집니다

근거는 위 표의 마지막 줄입니다. 파트너 한 명이 SDK를 못 찾아 클라이언트를 재구현했습니다.

### P2. 에러 메시지에 해결 경로를 담기

`크레딧 계정이 존재하지 않습니다`는 무엇을 해야 하는지 알려주지 않습니다.
Sandbox 충전금이 Live와 별도라는 사실과 `POST /credits/sandbox/charge`로 만들 수 있다는 사실이
메시지에 있었다면 지원 문의 없이 스스로 풀 수 있었습니다.

- 실패 지점에서 문서로 가는 딥링크를 `docsUrl` 같은 필드로 함께 내려주기
- 온보딩에서 자주 막히는 충전금 계정, `breakBefore`, multipart 여부부터 적용

`errorCode`가 문자열 enum인 점은 매우 좋았습니다. 사용자 메시지 분기를 문자열 매칭 없이 만들 수 있었고,
여기에 해결 경로만 얹으면 됩니다.

### P3. `breakBefore`를 form-data로 보내면 알려주기

지금은 조용히 무시됩니다. 내지 템플릿 기본값이 같은 페이지에 덮어쓰는 `none`이라,
파트너는 24번 호출했는데 페이지가 0인 상태를 원인도 모른 채 마주하고 finalize에서 튕깁니다.

- form-data에 `breakBefore`가 섞여 오면 400을 주거나 응답에 경고를 담기
- 또는 `contents` 응답에 `pageMeta.currentPageCount`를 항상 포함해 이상을 즉시 감지하게 하기

### P4. Sandbox 상태 전이 테스트 엔드포인트

Sandbox 주문은 `PAID`에서 멈춥니다. 합리적인 설계지만 **주문 현황 화면을 검증할 방법이 없습니다.**
`POST /webhooks/test`는 웹훅 수신 자체는 확인해주나 주문 상태를 실제로 전이시키지는 않습니다.

`POST /orders/{orderUid}/sandbox/advance`처럼 다음 상태로 한 칸 전이시키고 해당 웹훅을 발송하는 엔드포인트가 있으면,
파트너가 `PAID → CONFIRMED → IN_PRODUCTION → SHIPPED → DELIVERED` 전 구간을 실제로 확인할 수 있습니다.

### P5. 웹훅 `secretKey` 회전

최초 등록 시 1회만 전체 노출하는 정책은 안전합니다.
다만 분실 시 복구가 해제 후 재등록뿐이라, 그사이 이벤트 유실이 걱정돼 운영 중에는 회전을 미루게 됩니다.

`POST /webhooks/config/rotate-secret`으로 구 시크릿과 신 시크릿이 하루 정도 함께 유효하면 무중단으로 교체할 수 있습니다.

### P6. `GET /credits/transactions` 페이지네이션

쿼리와 페이지네이션을 지원하지 않아 거래가 쌓이면 클라이언트가 전량을 받아 직접 잘라야 합니다.
다른 목록 API와 같은 `limit`·`offset`이면 일관됩니다.

## 함께 보고 싶은 지표

개선이 실제로 효과가 있었는지 확인하려면 지표가 필요합니다.

| 지표 | 정의 | 왜 보나 |
|---|---|---|
| TTFO | API Key 발급부터 첫 주문 성공까지 걸린 시간 | 온보딩 마찰의 총합 |
| 첫 주문 전 이탈 지점 | 마지막으로 성공한 호출 단계의 분포 | 어디서 포기하는지 |
| 온보딩 구간 `errorCode` 상위 빈도 | 첫 주문 전에 발생한 에러만 집계 | P2에서 어떤 메시지부터 고칠지 |
| SDK·데모 도달률 | 문서, SDK, 데모 페이지 진입 비율 | P1의 효과 측정 |

## 잘 만들어져 있다고 느낀 것

- **일관된 응답 봉투** `{success, message, data, errorCode, errors, fieldErrors}` 덕분에
  클라이언트에서 언랩과 에러 처리를 한 곳으로 통일할 수 있었습니다.
- **`Idempotency-Key`** — 결제성 API에 가장 필요한 장치가 처음부터 있고 주문 문서에 반드시 포함하라고 못박혀 있습니다.
  4xx도 24시간 캐시하고 같은 키에 다른 본문이 오면 422로 막는 규약까지 문서에 있어서,
  고정 키를 쓰면 재시도가 잠긴다는 함정을 코드로 옮기기 전에 피할 수 있었습니다.
- **AI 에이전트용 문서** `llms.txt`, `llms-full.txt`, `.md` URL은 2026년 API 문서로서 인상적입니다.
  연동 후반 작업은 합본 하나를 컨텍스트에 넣고 진행했습니다. 다만 이 좋은 자산도 P1이 전제입니다.
- **환경 분리** — Base URL만 다르고 스키마가 같아 설정 하나로 전환되고,
  충전금도 Sandbox와 Live가 완전히 분리돼 테스트가 운영 잔액을 건드릴 걱정이 없었습니다.
